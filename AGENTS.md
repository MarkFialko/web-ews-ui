# OpenSpec — нейминг и apply-фаза

## Нейминг change-каталогов

Название каталога в `openspec/changes/` и `openspec/changes/archive/`:

```
PORTALSOL-NNNN/имя-описания    или    EWS-NNNN/имя-описания
```

- Jira-префикс (PORTALSOL-/EWS-) + тире + номер тикета
- Затем `/` + краткое описание на английском с дефисами вместо пробелов
- Пример: `openspec/changes/EWS-10410/add-worklog-to-tasks/`

## Apply-фаза

Во время реализации change по tasks.md:

- Редактируется только `tasks.md` (чекбоксы). `proposal.md`, `design.md`, `specs/` (дельты) не трогать.
- Не расширять scope сверх написанного в `tasks.md`.
- При расхождении между `design.md`/`tasks.md` и реальным кодом — остановиться, написать вопрос в отчёте, не додумывать.
- Archive (мёрж в основной specs/) не запускать самостоятельно — отдельный шаг после ревью.

## Промпты для слабой нейронки

`prompts/` — каталог с промптами для более простой/дешёвой модели, которой делегируется механическая часть реализации (например, отдельные задачи из `tasks.md`).

Структура зеркалит `openspec/changes/`:

```
prompts/PORTALSOL-NNNN/имя-описания/    или    prompts/EWS-NNNN/имя-описания/
```

- Путь совпадает с путём соответствующего change-каталога — по нему легко найти, к какому change относится промпт.
- Внутри — по одному md-файлу на промпт; для промптов, привязанных к конкретным задачам из `tasks.md`, нейминг `NN-краткое-описание.md`, где `NN` — номер задачи.
- Каждый промпт самодостаточен: содержит формулировку задачи, ссылки на нужные файлы, ограничения из `design.md` и критерий готовности — слабая модель не имеет доступа к остальному контексту change.
