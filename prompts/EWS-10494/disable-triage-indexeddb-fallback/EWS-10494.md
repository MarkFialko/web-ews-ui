# EWS-10494: отключить чтение triage-списка из IndexedDB и сбрасывать EngineerWorkspace в triage при отсутствии заявки

Этот файл самодостаточен — другого контекста change (proposal.md/design.md/tasks.md) для этой задачи нет,
весь необходимый контекст ниже. Не открывай и не меняй файлы, не упомянутые в разделе «Файлы».

## Контекст

`useTriageRequests` (`src/modules/triage/model/useTriageRequests.ts`) — хук, отдающий список заявок
инженера для triage-очереди. Сейчас у него два источника данных:

1. RTK Query (`useGetTriageRequestsQuery`) — основной источник, ходит на сервер.
2. IndexedDB-кэш (store `STORE_NAMES.TRIAGE`, ключ `"triage"`) — читается в `useEffect` при монтировании
   и используется как **fallback**, когда у серверного запроса ошибка (`hasServerError`) и в кэше есть
   свежая запись (`isCacheFresh`).

`EngineerWorkspace` (`src/modules/engineer-workspace/EngineerWorkspace.tsx`) определяет режим экрана
(`workspaceMode`: `"triage" | "ticket" | "tool"`) только по наличию `ticketId` в URL (функция `getMode`),
не проверяя, существует ли такая заявка вообще. Из-за этого при переходе по прямой ссылке на
несуществующую/недоступную инженеру заявку (либо когда triage-список пуст из-за ошибки сервера) workspace
всё равно пытается отрисовать `RequestCardModule` с этим `ticketId` — получается пустой/сломанный экран
вместо возврата к списку заявок.

Конкретный механизм поломки — цепочка `RequestCardModule` → `useOptimisticTaskCache`
(`src/modules/request-card/hooks/useOptimisticTaskCache.ts:111-114`) → `RequestCard.tsx:144`:

```ts
// useOptimisticTaskCache.ts
const task = useMemo(
  () => triageRequests.find((r) => r.businessId === taskId) ?? null,
  [triageRequests, taskId],
);
```

```tsx
// RequestCard.tsx
return taskData ? ( /* полная карточка */ ) : <RequestCardSkeleton />;
```

Данные карточки (`taskData`) уже берутся из `triageRequests` тем же способом (`find` по `businessId`). Если
заявки в `triageRequests` нет — `taskData` навсегда остаётся `null`, и `RequestCard` вместо ошибки/редиректа
бесконечно показывает `RequestCardSkeleton`. Обратный случай — когда заявка есть — уже работает сам по себе:
`useMemo` реактивно подхватывает её, как только `triageRequests` догрузится, и карточка сама переключается
со скелетона на полный рендер. Отдельная логика «показать тикет, если он есть» не нужна — нужна только
логика «уйти из этого экрана, если его нет» (см. пункт 2 ниже), иначе пользователь застревает на вечном
скелетоне.

## Что нужно сделать

### 1. Отключить чтение triage-списка из IndexedDB в `useTriageRequests`

Файл: `src/modules/triage/model/useTriageRequests.ts`

- Убрать состояние `cachedData` и `useEffect`, который читает запись из IndexedDB через
  `getStorageProvider().getRecord(STORE_NAMES.TRIAGE, CACHE_KEY)` и `isCacheFresh`.
- Убрать ветку `else if (hasServerError && cachedData) { triageRequests = cachedData; }` при вычислении
  `triageRequests` — при ошибке сервера (и отсутствии свежих серверных данных) `triageRequests` должен
  становиться пустым массивом (as в последней `else`-ветке).
- Убрать ставшие неиспользуемыми импорты: `getStorageProvider`, `STORE_NAMES` (из `@shared/cache`),
  `isCacheFresh` (из `@shared/cache/cacheLayer`), `CacheEntry` (из `@shared/types/cache`), и сам
  `CACHE_KEY`, если он больше нигде в файле не используется.
- Поведение `isLoading` / `isFetching` / `hasServerError` (что хук возвращает наружу) не менять — меняется
  только то, откуда берутся данные при ошибке сервера.

**Не трогать** запись в этот же IndexedDB store (`STORE_NAMES.TRIAGE`, ключ `"triage"`) — она остаётся как
есть и используется другими модулями:
- `src/modules/triage/api/index.ts` (`onQueryStarted` — кэширует успешный ответ сервера);
- `src/modules/ticket-actions/useTicketActionsPanel.ts` (~строка 307 — чистит закрытую заявку из кэша);
- `src/modules/request-card/api/index.ts` (несколько мест — синхронизирует оптимистичные обновления).

Эти файлы менять не нужно, задача только про чтение в `useTriageRequests`.

### 2. В `EngineerWorkspace` сбрасывать на triage, если заявки с таким `ticketId` нет

Файл: `src/modules/engineer-workspace/EngineerWorkspace.tsx`

- Сейчас хук вызывается так: `const { triageRequests } = useTriageRequests();` (строка ~107). Нужно
  дополнительно взять `isLoading`: `const { triageRequests, isLoading } = useTriageRequests();`.
- `closeRequest` уже деструктурирован из `useRequestsRouter()` в начале компонента и используется для
  сброса на список заявок (`navigate(ROUTES.REQUESTS)` внутри `useRequestsRouter`).
- Добавить `useEffect`, который после того, как triage-список загрузился (`!isLoading`), проверяет: если
  `ticketId` задан и среди `triageRequests` нет элемента с `businessId === ticketId` — вызвать
  `closeRequest()`.
- Эффект не должен ничего делать, пока список ещё грузится (`isLoading === true`) — иначе будет ложное
  срабатывание на первом рендере, до того как заявки успели подгрузиться.

Пример места и формы эффекта (расположить рядом с остальными `useEffect` компонента, после объявления
`chatBump`/после получения `triageRequests` и `isLoading`):

```tsx
useEffect(() => {
  if (!ticketId || isLoading) return;
  const exists = triageRequests.some((request) => request.businessId === ticketId);
  if (!exists) {
    closeRequest();
  }
}, [ticketId, isLoading, triageRequests, closeRequest]);
```

Тип элементов `triageRequests` — `RequestDTO` (`src/shared/request/types.ts`), поле `businessId: string`
у него уже есть.

**Не трогать**: логику `getMode`, `sourceRequestById`/`requestById` (это отдельный, не связанный с задачей
код — сейчас это всегда пустые `Map`, оставить как есть), рендер `WorkspaceToolPanel`/`ToolPanelShell` и
всё остальное в файле.

## Критерий готовности

- В `useTriageRequests.ts` не осталось обращений к IndexedDB/кэшу (`getStorageProvider`, `STORE_NAMES`,
  `isCacheFresh`, `CacheEntry`, `cachedData`) — `triageRequests` полностью зависит от результата
  `useGetTriageRequestsQuery`, при ошибке без свежих серверных данных возвращается `[]`.
- В `EngineerWorkspace.tsx` при открытии URL вида `/requests/ticket/:ticketId` с `ticketId`, которого нет
  среди `triageRequests` (после того как список загрузился), пользователя автоматически возвращает на
  `/requests`.
- Пока `triageRequests` ещё грузится (`isLoading === true`), автосброса не происходит.
- `npm run lint` и типовая проверка (`npx tsc --noEmit` либо `npm run build`) проходят без новых ошибок
  (включая отсутствие неиспользуемых импортов).
- Существующее поведение (открытие существующей заявки, переключение communication/tool-режимов) не
  сломано.
